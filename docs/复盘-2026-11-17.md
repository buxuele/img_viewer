# 交付复盘 2026-11-17

## 这次做错的地方

1. 平台判断错误。项目放在 macos_apps 目录下，我却先交付了 FastAPI 加浏览器的网页版。路径和“系统级 app”已经说明了交付形态，我没有先确认就选了技术栈，浪费了一整轮时间。
2. 核心动机后置。用户真正要解决的是 macOS 预览不能用鼠标滚轮放大图片，这件事直到用户明确说出来才写进 README。应该在第一次沟通时就把动机写进文档首段。
3. 擅自增加入口。用户要的是多窗口对比，我却顺手在文件菜单加了“新建窗口”。用户没有要求的东西不加，已有动作能完成的，不新增第二个控件。
4. 多窗口的生命周期没有先复现。冷启动双击图片时出现两个窗口，原因是打开文件事件可能早于 applicationDidFinishLaunching，先建了一个带图窗口，启动完成又补了一个空窗口。修法是启动完成时只在没有任何窗口时才建空窗口。
5. 验证方式打扰用户。为了看截图和窗口效果，反复启动 GUI，抢走鼠标焦点。用户还有别的事，这种验证方式不可接受。能离屏渲染就离屏，必须启动窗口时一次做完并提前说明。
6. 截图不符合交付标准。先只渲染 SwiftUI 内容区，没有标题栏；改成整窗截图后红黄绿按钮又是灰色。截图必须在活动窗口状态下抓，或者一次性处理好状态，不能反复来回试。
7. 文档写了没用的内容。README 里加了“演示图片来自 Wallhaven，编号 z8v3gy”这种自证式说明，用户直接指出没用。文档只写用户需要照着做或理解的信息。
8. 修复节奏不对。发现一个问题就启动一次应用，改一处再看一次，把调试过程变成了用户的等待。应该先复现、定位、改完，再一次性验证。

## 根因

1. 先动手后确认约束。没有先确认平台、交付物和运行方式。
2. 用开发便利代替用户视角。截图、窗口、菜单都是按自己方便来，没有按最终用户看到的形态检查。
3. 遇到问题做局部补丁。窗口多开、截图缺标题栏、按钮变灰，都是补一处看一处，没有先想清楚完整状态。
4. 把“验证”当成了可以随时打断用户的事。GUI 弹窗和焦点抢占的代价没有被计入。

## 以后必须这样做

1. 先确认平台和交付物。路径、项目名、运行环境已经限定平台时，直接按该平台原生方案做，不再用浏览器包装替代。
2. 先写用户动机。README 第一段写清楚这个工具解决什么具体问题，再写功能和运行方式。
3. 不擅自加控件。用户没要求的菜单项、按钮、开关一律不加；一个动作只对应一个入口。
4. GUI 验证一次完成。优先离屏渲染和单元测试；必须启动窗口时提前说明，批量完成，不反复抢焦点。
5. 截图按最终形态验收。必须是完整窗口，包含标题栏和红黄绿按钮，位置、层级、字号、多余控件都要自查。
6. 文档只留有用信息。不写来源自证、过程炫耀、无关注释；判断标准是用户会不会照着看。
7. 先复现再修。尤其是窗口生命周期、文件打开事件顺序这类问题，先用真实双击文件复现，再改代码。
8. 同类问题一次改完。多窗口、截图、文档、菜单入口这些点，收敛成规则写进项目记录，不重复犯。

## 本次留下的技术结论

1. application(_:open:) 可能早于 applicationDidFinishLaunching。启动完成时只有在 contexts 为空时才创建空窗口，否则会多出一个空窗口。
2. 每个窗口持有独立的 AppModel，菜单和快捷键只作用于当前窗口的模型；空白窗口复用，已有图片时打开新图片才新建窗口。
3. 只渲染 ContentView 的截图没有窗口 chrome。要得到完整窗口，必须在真实 NSWindow 的活动状态下抓取，或者明确接受非活动窗口的灰色按钮状态。
4. 窗口截图和界面验证都应该由一次脚本批量完成，不能边改边弹窗。
